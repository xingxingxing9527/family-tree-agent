# 父母关系自动补全与关系维护设计

日期：2026-10-01

状态：待用户书面复核

关联规格：[家谱智能体 Web MVP 产品与技术设计](./2026-10-01-family-agent-web-mvp-design.md)

## 1. 目标

管理员在普通夫妻家庭中只需为孩子录入一次父亲或母亲关系。系统根据已确认的婚姻事实，在结构化预览中默认补出另一位生物学父母；管理员确认后，两条亲子关系作为同一个操作组写入并可整体撤销。

该能力用于减少重复录入，不代表系统可以静默猜测亲属事实。任何自动补全都必须显示人物、关系、匹配依据和来源，允许管理员取消；无法唯一判断时不自动选择。

## 2. 已确认的产品决定

- 自动补全在统一业务规则层实现，不局限于某个网页表单。
- 只有一个配偶候选时，默认将其补为孩子的另一位生物学父母。
- 有多段婚姻时，优先依据孩子出生时间与婚姻时间区间进行保守匹配；无法唯一判断时由管理员选择或暂时跳过。
- 没有婚姻记录时，只保存已明确录入的亲子关系，并提示“另一位父母尚未确认”；不创建占位人物。
- 首版仍只建模生父、生母。遇到继父母、养父母等情况，管理员取消或移除自动补全的生物学关系，婚姻关系继续保留；不新增复杂亲属类型。
- 新关系使用自动补全；现有“仅录入一位父母”的数据只生成批量修复预览，管理员确认后才写入。
- 人工确认的关系优先于系统建议，系统不得覆盖已有父亲或母亲。

## 3. 范围

### 3.1 包含

- 新增亲子关系时规划、预览并可选地写入配偶对应的另一条亲子关系。
- 对现有数据扫描可安全补全的关系并生成批量预览。
- 在人物详情中以当前人物为中心维护父亲、母亲、配偶和子女。
- 对单条亲子关系执行移除或“移除旧关系并添加新关系”的原子更正。
- 保存自动补全来源，并在人物详情、预览和历史中显示。
- 普通婚姻、离婚、再婚、日期缺失和父母冲突的校验与测试。

### 3.2 不包含

- 继父、继母、养父、养母、收养、监护等新关系类型。
- 自动创建未知人物或占位人物。
- 未经管理员预览确认直接批量修改现有数据。
- 因婚姻后来离婚或被修改而自动删除已经确认的亲子关系。
- 使用性别字段替代明确的“父亲/母亲”角色选择。

## 4. 领域语义

### 4.1 明确事实与系统建议

管理员主动选择的人物、子女和父母角色构成“明确亲子事实”。配偶自动补全构成“系统建议”。系统建议默认选中，但在确认前可以取消；确认后成为普通的有效生物学亲子事实，同时保留其生成来源。

系统只根据已经存在的婚姻记录寻找候选，不因为姓名、性别、同住或称谓自行创建婚姻或人物。

### 4.2 角色补全

- 明确关系为“父亲”时，候选配偶补为“母亲”。
- 明确关系为“母亲”时，候选配偶补为“父亲”。
- 人物性别未知不阻止角色补全。
- 人物性别与拟补角色明显不一致时显示警告，但不依赖性别自动改写管理员选择。

### 4.3 婚姻候选选择

先按配偶人物去重，再按以下顺序处理：

1. 没有候选配偶：不补全，返回“另一位父母尚未确认”。
2. 只有一个候选人物：默认选择该人物。即使同一对人物存在多段婚姻，其父母人物仍然唯一。
3. 有多个候选人物：使用孩子出生日期与各段婚姻的开始、结束日期进行保守区间比较。
4. 仅当一个候选能明确包含孩子出生时间，且其他候选能明确排除时，才自动选择。
5. 日期缺失、历法不同、精度不足或多个候选均不能排除时，返回候选列表，由管理员选择或跳过。

沿用现有部分日期的区间语义，不把缺少“日”的日期擅自补成某一天，也不自动换算公历和农历。

### 4.4 已有父母处理

- 目标角色不存在：可以生成补全建议。
- 目标角色已经是同一人物：预览显示“无需变更”，不创建重复记录。
- 目标角色已经是另一人物：补全建议标记为冲突且不可选择，不覆盖已有关系。
- 明确录入的关系本身违反唯一父母、祖先环或自关联规则时，整条明确关系被阻断。
- 只有可选的自动补全项发生冲突时，不阻止管理员保存合法的明确关系。

## 5. 应用架构

### 5.1 高层意图

新增高层亲子录入意图 `parentFamily.add`，至少包含：

- 已明确的父母人物 ID。
- 子女人物 ID。
- 明确父母角色。
- 补全策略 `spouse-default`。
- 可选的管理员指定配偶 ID。
- 来源说明。

现有低层 `parentChild.add` 继续代表一条明确的数据库事实，供规划结果、关系更正和内部流程使用。表单、对话及未来支持关系的导入入口应优先产生高层意图，避免各入口自行复制补全算法。

### 5.2 父母补全规划器

新增独立领域组件 `ParentCompletionPlanner`。它只负责读取人物、婚姻、出生日期和现有亲子关系，返回确定性的规划结果，不直接写库。

规划结果包含：

- 明确亲子关系。
- 可选的自动补全关系。
- 补全依据：唯一配偶、出生时间唯一匹配或管理员指定。
- 候选配偶列表。
- 无候选、歧义、无需变更或冲突状态。
- 面向管理员的中文说明及机器可识别的问题代码。

该组件被新增录入、现有数据扫描和测试共同复用。

### 5.3 结构化预览与提交

暂存变更服务在预览阶段把一个 `parentFamily.add` 展开为一条或两条低层亲子变化：

- 明确关系始终列出。
- 可安全补全的关系以“系统自动补全”标记并默认选中。
- 歧义候选要求管理员修订草稿，指定配偶或跳过补全。
- 冲突的自动项显示为不可选择的阻断项，但不使合法的明确关系失去可提交性。
- 被管理员取消的自动项不写入。

两条有效且被选中的关系在一个数据库事务和一个操作组中提交。提交前重新执行候选选择、行版本和领域校验；数据在预览后发生变化时返回冲突，要求刷新预览。

### 5.4 数据与来源

为 `parent_child` 增加以下元数据：

- `origin_kind`：`explicit` 或 `spouse_default`，已有记录迁移为 `explicit`。
- `inferred_from_marriage_id`：能够唯一确定婚姻事件时记录该事件；配偶人物唯一但具体婚姻事件仍不明确时允许为空，明确录入时也为空。

自动补全同时创建来源说明，例如“根据父母婚姻关系自动补全”。一旦管理员确认，亲子关系不会随着婚姻状态后续变化被自动删除；来源元数据只用于解释和更正。

### 5.5 单条关系维护

共享变更接口新增：

- `parentChild.remove`：按关系 ID 和预期版本软删除一条亲子关系。
- 关系更正通过同一暂存草稿组合 `parentChild.remove` 与 `parentChild.add`，在一个操作组中提交。

删除自动补全的亲子关系不得删除人物或婚姻记录。撤销操作恢复该亲子关系，并继续遵守现有后续依赖检查。

### 5.6 现有数据修复

新增只读扫描服务，查找只有一位有效父母的孩子，并逐个调用同一补全规划器。扫描结果分为：

- 可唯一补全。
- 无候选配偶。
- 多候选且无法判断。
- 已有父母冲突。

扫描本身不写库。管理员选择建议后，系统生成普通暂存草稿，继续经过预览、版本检查、确认、事务、审计和撤销流程。批量提交时任何并发版本冲突都会阻止整组写入，避免只修复一部分。

## 6. 界面设计

### 6.1 人物中心关系面板

人物详情将当前人物固定为中心，分为父亲、母亲、配偶和子女四个区域。管理员不再重复从全量名单中选择当前人物。

- 父亲、母亲通常各一条。
- 配偶和子女支持搜索与多选。
- 每个关系位置支持选择已有成员；快速创建新人物仍走统一预览。
- 每条关系显示人物姓名、关系角色、来源类型，并提供“更正”和“移除”。
- 自动补全的关系显示“系统自动补全”标记及其依据。

新增子女时，预览应同时展示当前人物的明确关系和配偶的自动补全关系。例如：

- `刘雁杰 → 悠悠：母女（人工录入）`
- `李云龙 → 悠悠：父女（根据婚姻自动补全）`

### 6.2 歧义与缺失状态

- 无配偶：显示“另一位父母尚未确认”，允许仅保存明确关系。
- 多候选：显示候选人物、婚姻时段和匹配依据；管理员可以选择一人或暂时跳过。
- 冲突：显示现有父母与拟补父母，不提供覆盖按钮；需进入关系更正流程。
- 树节点“仅录入一位父母”继续表示数据完整度，不表示婚姻状态。

### 6.3 批量修复入口

在人物或关系管理区域提供“检查未完整父母关系”入口，显示统计和逐条建议。可唯一判断的建议默认勾选；无候选、歧义和冲突只展示问题，不进入批量提交。管理员可以逐条或全选可安全项目，再进入统一预览。

## 7. API 与契约

HTTP API 与共享应用契约至少增加：

- 暂存高层 `parentFamily.add` 意图。
- 查询单条亲子关系 ID、行版本和来源元数据。
- 扫描未完整父母关系并返回建议。
- 暂存 `parentChild.remove` 及组合更正。

服务端重新执行规划和校验，不信任前端提交的“自动补全”结论。管理员指定的候选必须仍然是相关婚姻中的配偶，且不能违反父母唯一性或祖先环规则。

## 8. 错误与并发处理

- `PARENT_COMPLETION_AMBIGUOUS`：存在多个无法唯一判断的配偶候选。
- `PARENT_COMPLETION_NO_CANDIDATE`：没有婚姻候选；作为信息提示，不阻断明确关系。
- `PARENT_ROLE_OCCUPIED`：目标父母角色已有另一人物；自动项不可选。
- `PARENT_COMPLETION_STALE`：预览后婚姻、人物、出生日期或亲子关系发生变化。
- 继续使用现有自关联、祖先环、跨工作区和版本冲突错误。

错误信息必须显示中文人物姓名和关系，不只显示内部 ID。可选自动项失败时不得伪装成整次录入失败；明确关系本身失败时则禁止提交。

## 9. 数据迁移与兼容性

- 数据库迁移为已有 `parent_child` 记录设置 `origin_kind = explicit`，不改变现有亲子关系。
- 首次升级不自动补全历史数据。
- 现有低层新增亲子 API 保持可用，但普通用户入口逐步迁移到高层意图。
- 旧客户端无法识别来源元数据时仍能读取基础亲子关系；写入仍由服务端校验。
- 批量修复必须由管理员主动打开、选择并确认。

## 10. 测试策略

### 10.1 领域单元测试

- 唯一配偶自动生成互补角色。
- 同一配偶的多段婚姻仍得到唯一人物候选。
- 多个配偶按孩子出生区间唯一匹配。
- 日期缺失、历法不同、区间重叠时保持歧义。
- 已有相同父母返回无需变更，已有不同父母返回冲突。
- 无配偶只返回明确关系和信息提示。

### 10.2 应用与集成测试

- 一条高层意图展开为两条关系，并在一个操作组提交和撤销。
- 取消自动项后只写入明确关系。
- 自动项冲突时仍可提交合法的明确关系。
- 预览后婚姻或父母关系变化会触发版本冲突。
- 移除自动关系不影响婚姻；组合更正保持事务原子性。
- 现有数据扫描不写库，确认的批量修复才产生审计记录。

### 10.3 界面与端到端测试

- 人物中心界面无需重复选择当前人物。
- 普通夫妻为孩子录入一次后，预览双方父母并正确显示来源。
- 离婚、再婚、缺失日期和多个候选分别显示正确状态。
- 管理员能够取消自动补全、移除错误关系并撤销操作。
- 批量修复后，父母完整的孩子不再显示“仅录入一位父母”。

## 11. 验收标准

- 普通夫妻家庭只录入一次即可建立孩子与双方父母的关系。
- 任何自动补全都在确认前可见、可取消、可解释。
- 没有配偶或无法唯一判断时不猜测、不创建占位人物，也不阻止保存明确关系。
- 人工事实不会被自动建议覆盖。
- 两条关系能够一次写入和一次撤销。
- 自动关系可单独移除，且婚姻关系不受影响。
- 现有数据只在管理员确认批量修复后改变。
- 人物详情、家谱树、称谓计算、问答和导出读取相同的已确认亲子事实。

## 12. 对主规格的修订

本设计对主规格作以下窄范围修订：

- “不自动推断或生成不存在的关系”调整为“不静默创建人物或关系；允许根据已确认婚姻生成可取消的父母补全建议，并在管理员确认后写入”。
- “父母信息不完整时不猜测另一位父母”调整为“显示不完整状态；可以按本设计提出候选，但歧义时不得自动选择，未经确认不得写入”。
- 关系录入主入口调整为以人物为中心；原“两人建立关系”表单保留为高级或纠错入口。
